The Element Has a Name

August 5, 2026 · ~3,500 words · 10 live figures, a recall drill, and a quiz · reading this as an AI agent? agents.md is for you

The fastest way to get the wrong control built is to call it a "dropdown." That one word covers at least five different components with five different behaviors, and the agent writing my markup has to guess which one I meant. Last month I asked for "a dropdown to filter the chart" on the server dashboard and got a <select> element. I wanted a menu of actions. The word was the whole spec, and the word was wrong.

Nielsen Norman Group solved the vocabulary problem in February 2025: Raluca Budiu and Kara Rivenbark published a glossary that names 61 interface elements with their alternate names and one-line definitions. The Component Gallery does the cross-referencing job from the other end - 60 components as they appear across 95 real design systems, so you can see what Ant Design, Polaris, and the BBC's Global Experience Language each call the same thing. Between them, almost every argument I have ever had about a control has a settled answer.

So this post is not an article about UI elements. It is a specimen sheet: 102 live elements, each one labeled with its canonical name, the family it belongs to, and the synonym most likely to get you the wrong thing. Nothing here is a screenshot. Every menu opens, every dialog is a real <dialog>, every popover uses the browser's top layer. Toggle the labels off and this is an ordinary page; toggle them on and it is a catalog of itself.

The teaching structure comes from Geoffrey Litt's talk "Understanding: the New Bottleneck," which I keep raiding for this: demonstration over description, and a quiz at the end because, as Andy Matuschak puts it in "Why Books Don't Work," reading hands you the feeling of understanding and almost none of the retention. You will not remember the difference between a kebab and a meatball menu because I told you. You might remember it because you clicked both.

Five controls, one word

Start with the argument that started this. Below are the five things people mean by "dropdown," side by side and working. The differences are not cosmetic. Two of them run commands and three of them hold a value; two accept input that is not on the list; only one of the five is a single native HTML element.

The obvious objection: does this level of pedantry pay for itself? It does now, and it did not five years ago. When I wrote the markup myself, a wrong word cost me the ten seconds it took to notice and fix. Now the word goes to an agent that produces 200 lines of confident, working, wrong component, and the cost is the review. Precision in the prompt is cheaper than precision in the diff.

Five families, and the sources do not agree on how many

Elements group into functional families, and here I have to be honest about the taxonomy: nobody agrees on the count. UXPin's guide sorts everything into four top-level categories - input, output, navigational, and container. NN/g's glossary does not impose top-level families at all; it is 61 alphabetical entries. The five-family split I use below - navigation, input, feedback and status, display and containers, and page-level blocks - is a working convention, not a standard. What matters is that the element names are canonical. The bins are mine.

The switchboard above filters by family and searches names plus synonyms, so if you only came for the input controls, click "Input" and the rest fade out.

Navigation: how people move, and the four menu icons

Navigation elements answer "where am I and where can I go." The four snack-food icons in the middle row are the ones I see mislabeled most. LogRocket's Rosie Allabarton gives the crisp version: the hamburger is three horizontal lines, the kebab is three dots arranged vertically, the meatball is three dots arranged horizontally, and the bento is a grid of squares. Click each one - the contents differ on purpose. Hamburger opens site navigation, kebab and meatball open item-scoped actions, bento switches between apps.

Input controls: the ones with the most synonyms

Input is where the naming gets sloppiest, because every design system renames the same six things. NN/g's canonical entries are Textbox (Text Field, Input Field), Toggle (Toggle Switch, Switch), Segmented Button (Segmented Control), Floating Button (FAB), Range Control (Continuous Control), and Input Stepper. If you say "switch" to a designer and "toggle" to an engineer you are naming the same element twice.

Feedback and status: modality is a property, not a component

The distinction worth carrying out of this section: "modal" is not a component, it is a mode. A dialog is the component. Calling showModal() on a <dialog> puts it in the top layer, renders a ::backdrop, and makes everything behind it inert. Calling show() on the same element gives you a non-modal dialog that leaves the page usable. Same element, same markup, different mode - and the bottom sheet, the drawer, and the lightbox in Fig. 4 are all that same <dialog> element with different CSS.

Display and containers: the boxes everything else sits in

Container names are the least standardized and the most consequential, because they set your layout vocabulary for the life of the codebase. MUI calls its elevated surface a Paper; Material 3 calls it a Surface; Bootstrap has no equivalent and you use a Card. The layout primitives at the end - Box, Stack, Grid, Container - come from MUI and have been widely copied; the Component Gallery lists Stack as a component in its own right.

How much of this does the browser ship already?

Before you scroll into Fig. 7, make a prediction. Of the 18 interface capabilities listed there - dialogs, popovers, exclusive accordions, anchor positioning, customizable selects, scroll-driven animation, and so on - how many do you think your browser supports natively today? Write the number down. Most engineers I have asked guess somewhere between 6 and 10, and they are reliably low, because the mental model was set when jQuery plugins were how you got a modal.

Then press the button. The probe runs real feature detection in your browser - CSS.supports(), prototype checks, and element construction - and reports what is actually there.

Firefox and Safari will score lower on the last five rows, which is the whole reason to run the test in your browser instead of trusting my number.

The result I did not expect when I built this: on Chrome 142 the score is 18 out of 18. The modal dialog, the popover menu, the exclusive accordion, the anchor-positioned tooltip, the color picker, and even the carousel scroll buttons are native now. A component library still earns its place on theming, on keyboard behavior in the edge cases, and on consistency across a team - but no longer on making the browser do things it cannot do. That was not true in 2019, and my instincts had not caught up.

The names that collide

These are the collisions that have actually cost me time. Each one is a case where two sources use the same word for different components, or different words for the same component.

NameThe collision
StepperThe Component Gallery's "Stepper" is the multi-step wizard. NN/g's "Input Stepper" is the numeric increment/decrement control. Two unrelated components, one word. Say "wizard" or "number input" and the ambiguity disappears.
BadgeBootstrap's badge is a small inline label - what Material calls a chip and Polaris calls a tag. Material's badge is the count bubble on an icon. NN/g follows Material: "notification indicator (dot) or item counter."
ModalNot a component. It is a property of a dialog: showModal() versus show(). Ask for "a modal" and you have specified the mode but not the content pattern.
Snackbar / toastMaterial says snackbar, everyone else says toast. NN/g lists it as "Snackbar (Toast)." Same element.
Drawer / side sheet / flyoutThree names, one element. NN/g's entry is "Side Sheet (Drawer, Flyout)"; it also lists "Drawer Menu" separately for the navigation-specific case.
Segmented controlApple's name. Material 3 says segmented button; NN/g lists "Segmented Button (Segmented Control)." Bootstrap has no equivalent and you build it from a button group.
PopoverAmbiguous in a way the others are not: it is both a component name (NN/g "Popup (Popover)") and an HTML attribute that is a top-layer mechanism. The menus, tooltips, and hover cards in this page are all built with popover but are not all a popover.
CardThe most overloaded container in the industry. NN/g pins it usefully: "container resembling playing card size holding related brief information." If it fills the page it is a panel or a surface, not a card.

Recognition is not the skill you need

I built the quiz below before I had thought hard enough about what it measures. It is multiple choice, so it tests recognition: shown four names, can you pick the right one. But the thing this post is supposed to buy you happens at a blank prompt box, where nobody offers you four options. That is recall, and the two are not the same skill. Robert and Elizabeth Bjork's distinction between fluency strength (how easily something comes to mind right now) and storage strength (how durably it is learned) is the reason multiple choice feels productive and mostly is not: recognizing a name you just read scores high on fluency and adds almost nothing to storage.

Their prescription is desirable difficulty - make the retrieval harder on purpose - and the cleanest instance of it is the testing effect that Henry Roediger and Jeffrey Karpicke measured in 2006: students who were tested on material retained substantially more than students who restudied it for the same time, even though the restudy group felt more confident. Matt Pocock's teach skill builds a whole workspace around the same pair of ideas, and it names the thing I had skipped: skills require effort and a tight feedback loop, not a comprehension check at the end.

So Fig. 9 is the harder version. It shows you a specimen lifted live out of this page - the actual DOM node, cloned, with its label stripped - and asks you to type what it is called. No options. It accepts the canonical name or any of the synonyms this page has taught you, which is the honest grading rule: "side sheet" and "flyout" are both correct for a drawer.

The quiz at the door

Litt's rule for his own agents is that a PR does not ship unless he could pass a quiz on it. Same rule here, and the same warning from Matuschak: if you scrolled and nodded, you kept almost none of it. Six questions - and having just done the recall drill, notice how much easier these feel. That gap is the point.

Fig. 10 · Pass the quiz before you name it
1. A user must pick exactly one of twelve known countries, and must not be able to enter anything else. Which control is that?

A dropdown list - one native <select>. A combo box would let them type "Freedonia," a dropdown menu runs commands rather than holding a value, and an autocomplete implies an open-ended option set.

2. What actually makes a dialog "modal"?

Modality is a mode, not a component. The same <dialog> element gives you both: showModal() for modal, show() for modeless. Both are in Fig. 4.

3. Three dots arranged vertically. What is that icon called?

Kebab is vertical, meatball is horizontal, hamburger is three lines, bento is a grid. Picture the skewer standing up.

4. Your ticket says "add a stepper." Why is that ticket ambiguous?

NN/g's "Input Stepper" adjusts a number in fixed increments. The Component Gallery's "Stepper" is the wizard with numbered stages. Both are in this page, in Figs. 3 and 2 respectively.

5. A checkbox and a toggle switch both hold a boolean. When do you reach for the switch?

A switch is an immediate state change - flip it and the setting is applied. A checkbox collects a value the form submits later. NN/g files the switch under "State-Switch Control."

6. Which of these is a browser mechanism rather than a named component?

popover is a top-layer primitive with light-dismiss and focus management built in. The dropdown menus, tooltips, hover cards, and pie menu in this page are all built with it, and none of them is "a popover" as a component name.

What's still open

The honest limit of this page is that a vocabulary does not settle an argument by existing. NN/g published 61 canonical names in February 2025 and the design systems in the Component Gallery still disagree with each other and with NN/g - 95 systems, and "stepper" still means two different things depending on which door you came in. I have not adopted a house glossary across my own repositories yet, and until I do, this post is a reference I wrote rather than a standard I follow. That is the next piece of work: a short names file in each project so the agent and I are reading from the same list, which is a smaller and more useful artifact than another design system.

The second open question is whether the labels helped. Litt's own caveat about interactive figures is that they can become a crutch - you push the buttons, feel competent, and retain nothing. Adding the recall drill sharpened that worry rather than settling it: I can now measure whether you produce the word, but only for the 24 specimens in the pool and only in the same session, which is precisely the fluency-strength reading the Bjorks warn is the misleading one. The honest experiment is a drill that comes back in a week, and a page cannot do that. My own answer is that building this taught me two things I did not know going in: that <details name> makes an exclusive accordion with no JavaScript, and that a "modal" was never a component in the first place. Whether reading it does the same for you is the test I still cannot run.
