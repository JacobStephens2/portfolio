vaulted-agent v0.3.0

Launch Claude Code, Codex, Grok, or Kimi Code with vault-resolved secrets in the process - not in a pile of .env files. One vault, one launcher, different blast radius per agent. Optional prompt auth so even the vault token need not live on disk. Same path for one-shot tools via va run.

Install

macOS and Linux. One-liner bootstraps a tagged GitHub release (default pin v0.3.0, not floating main). Installs vaulted-agent + va, detects claude / codex / grok / kimi on PATH with workdir = caller, and can prompt for a vault backend plus auth mode. Override pin: VAULTED_AGENT_VERSION=v0.3.0 (or latest).

One-liner macOS · Linux 
curl -fsSL https://stephens.page/vaulted-agent/install.sh | bash
From GitHub macOS · Linux 
git clone --branch v0.3.0 --depth 1 \
  https://github.com/JacobStephens2/vaulted-agent-launcher
cd vaulted-agent-launcher && sudo ./install.sh
Uninstall macOS · Linux 
sudo vaulted-agent uninstall
# or:  sudo va uninstall
# also remove config:  sudo vaulted-agent uninstall --purge

After install: va setup

Day-one harnesses start as plainfile + empty.env (agents launch, but with no vault secrets). Wire a backend next. Lifecycle as you scroll: install → setup → launch agents → optional va run / doctor.

  1. Install the launcher (above). Auto-detect writes harnesses for any of claude, codex, grok, or kimi already on PATH.
  2. Setup a vault with va setup - pick a backend, supply a token, optionally build a refs file (env var → secret reference, never the secret value).
  3. Point harnesses at that refs file (backend = bitwarden and manifest = openai.env.refs), or use va run -m … for one-shots.
  4. Check, then launch: va doctor → va claude / va grok -p / va kimi.
Run setup interactive TTY 
va setup
# same binary:
vaulted-agent setup

Usage

Name the harness as the first argument. After install, if those CLIs were on your PATH, harnesses are auto-created so these work immediately (no vault secrets until you configure a backend). Short alias va is the same binary.

Launch an agent everyday 
va claude
va codex
va grok
va kimi                  # Kimi Code CLI if on PATH
va pick
# full name also works:
vaulted-agent claude
Wire a vault · check health after install 
va setup                 # backend / token; Bitwarden can build a refs file
va auth-mode             # file (token on disk) vs prompt (paste each launch)
va doctor                # harnesses, CLIs, manifest syntax (no secret values)
va version               # e.g. vaulted-agent 0.3.0
va claude -p             # force token prompt this launch only

One-shot commands: va run

Inject a manifest into any command without writing a harness file. Same scrub → resolve → drop vault token → exec path as va claude. Useful for scripts, deploys, and tools like gpt-image. 

va run -m openai.env.refs --backend bitwarden -p -- \
  python gpt_image.py generate "a lighthouse in a storm, gouache" \
  --output out.png

va run -m readonly.env --backend plainfile -- env | sort

-m is a refs file under /etc/vaulted-agent/manifests/ (or an absolute path). -p pastes the vault token for that launch only and never writes it.

Auth modes: where the vault token lives

Machine-wide default is /etc/vaulted-agent/defaults.conf (auth_mode = file|prompt. Set at install (--auth-mode) or later with va auth-mode. Per-launch override: -p / --prompt-auth.

Mode Token provision On disk
prompt Paste at each launch (TTY). Also if parent already exported the token. Nothing written by the launcher.
file Read from a dotenv file at launch. 1Password: /etc/vaulted-agent/op.env
Bitwarden: /etc/vaulted-agent/bws.env
Mode 0640, root + service-user group.

Resolved secrets (API keys, DB passwords) are never written by the launcher. Only the optional vault manager token can be. With auth_mode=prompt, even that stays out of disk. va setup only writes bws.env when auth mode is file; under prompt it says so and continues in-process only. 

va auth-mode show
va auth-mode prompt          # paste SM / OP token each launch
va auth-mode file            # use op.env / bws.env
va setup                     # interactive backend help
# Bitwarden + nothing on disk from day one:
#   curl … | bash -s -- --backend bitwarden --auth-mode prompt

Bitwarden Secrets Manager

The bitwarden backend is Secrets Manager (bws), not the personal vault CLI. The credential is a Machine Account access token (BWS_ACCESS_TOKEN - not your vault master password and not a login API key. Wrong type fails with errors like “Doesn't contain a decryption key.”

Manifests hold references only (safe to leave world-readable). Supported forms:

Ref formExample
UUIDOPENAI_API_KEY=6a1c0e94-…
uuid:OPENAI_API_KEY=uuid:6a1c0e94-…
name:OPENAI_API_KEY=name:openai-api-key
project:/OPENAI_API_KEY=project:tools/openai-api-key

Placeholders (REPLACE_…, all-zero UUIDs, …) fail validation before launch - in va doctor, va secrets validate, and every real launch.

va setup → Bitwarden can list secrets and write a refs file (filename under /etc/vaulted-agent/manifests/, e.g. openai.env.refs). That file maps env var names to name:… / UUID lines. It never stores secret values or the access token. Point a harness with backend = bitwarden and manifest = openai.env.refs, or use va run -m openai.env.refs ….

Doctor & secrets helpers

va doctor

Version, service user, auth mode, whether bws/op/sops/pass are on PATH, auth files present, each harness’s backend/manifest/workdir, and manifest syntax. No secret values.

va secrets

list · get <ref> · which (harness → var names only) · validate. Same token prompt/file rules as launches.

va version

Prints vaulted-agent 0.3.0. The remote installer pins the same series so README and one-liner stay aligned.

va doctor
va secrets list
va secrets get name:openai-api-key
va secrets which
va secrets validate
va secrets validate openai.env.refs bitwarden

How it works

Treat the agent as the unit of authorization. A harness names a command and a manifest; the launcher becomes the service account, scrubs the environment, resolves that manifest into the process, drops the vault token, and execs. Diff the manifests and you have a written answer to “which agent could reach what.” Secrets live in that process until it exits. 

you $ va claude --resume <id>
      │
      ▼
  /usr/local/bin/vaulted-agent   (alias: va)
      ├─ optional sudo -u <service>    become the service account
      ├─ cd workdir                    caller cwd by default (sessions / resume)
      ├─ scrub environment             allowlist only; nothing inherited rides along
      ├─ load vault auth               op.env / bws.env, or prompt (auth_mode)
      ├─ resolve manifest refs         op inject / bws secret get / …
      ├─ unset vault token             agent must not inherit the master key
      └─ exec claude … --resume <id>
             └─ secrets live here, until the process exits
Claude Code Codex Grok Kimi Code va run 1Password · Bitwarden SM · pass · sops prompt auth bash · sudo

What you get

  • One vault token on disk (or none, with prompt auth) instead of a fleet of .env files
  • Central rotation - change the vault, every future launch picks it up
  • Diffable manifests: which agent can reach what
  • Nothing secret on the command line (ps stays clean)
  • va run for tools and scripts without a harness file
  • doctor / secrets validate fail closed on placeholders

Honest limits

  • Not “zero secrets on disk” when using auth_mode=file - one service-account token remains
  • The agent can read its own environment (and so can anything as that user)
  • Manifests are blast-radius control, not containment - with file auth the agent can still open the token file
  • No TTY for token prompt when one agent shells out to another - use file auth or export the token in the parent
  • Root on the host can still read everything

Publishing forced five bug fixes (here-strings spilling to /tmp, the vault token riding along, missing environment scrub, exported bash functions, broken per-path sudoers). Full walkthrough: One Vault, Three Agents.

Install flags & resume

Prefer not to pipe to bash? Download install.sh, read it, then bash install.sh. Pin with VAULTED_AGENT_VERSION=v0.3.0. Useful flags after bash -s --: --backend bitwarden --auth-mode prompt, --no-va, --no-auto-harness, --backend onepassword --op-token-file ./token. Install rewrites the launcher’s default backend from --backend and prints the matching token path (bws.env vs op.env).

Session resume is normalized across agents (Claude/Grok use --resume; Codex uses the resume subcommand; Kimi Code uses --continue / --session, with bare resume rewritten). Harnesses default to workdir = caller so sessions match the directory you launched from. Auto-detect also wires kimi when the Kimi Code CLI is on PATH.

va claude --resume b03ca221-798e-457b-8f64-f71713e7066c
va claude resume b03ca221-798e-457b-8f64-f71713e7066c
va codex resume 019fabc2-fe4f-7e00-a431-a6a44d94b559
va grok --resume 019fabde-7535-7cc2-ab09-7987edc08ff8
va kimi --continue
va kimi --session abc123
va kimi resume abc123
