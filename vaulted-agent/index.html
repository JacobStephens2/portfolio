vaulted-agent

Launch Claude Code, Codex, or Grok with vault-resolved secrets in the process - not in a pile of .env files. One vault, one launcher, different blast radius per agent.

Usage

Name the harness as the first argument. That is the everyday interface - the same commands used in day-to-day work after a harness is configured.

Launch an agent everyday 
vaulted-agent claude
vaulted-agent codex
vaulted-agent grok
vaulted-agent pick
Short alias same binary 
va claude
va codex
va grok
va pick

Install

macOS and Linux. One-liner bootstraps a tagged GitHub release (not floating main). Installs vaulted-agent and the short alias va. Then activate harnesses and put your vault token in op.env.

One-liner macOS · Linux 
curl -fsSL https://stephens.page/vaulted-agent/install.sh | bash
From GitHub macOS · Linux 
git clone --branch v0.1.3 --depth 1 \
  https://github.com/JacobStephens2/vaulted-agent-launcher
cd vaulted-agent-launcher && sudo ./install.sh
Uninstall macOS · Linux 
sudo vaulted-agent uninstall
# or:  sudo va uninstall
# also remove config:  sudo vaulted-agent uninstall --purge

How it works

vaulted-agent claude (or codex, or grok) becomes a dedicated service account, resolves that harness’s manifest into the process environment, drops the vault token, and execs the agent. Diff the manifests and you have a written answer to “which agent could reach what.” Secrets live in that process until it exits. 

you $ vaulted-agent claude
      │
      ▼
  /usr/local/bin/vaulted-agent
      ├─ sudo -u agent                 become the service account
      ├─ scrub environment             allowlist only
      ├─ op inject -i full.env.tpl     vault refs → values, in memory
      ├─ unset vault token             agent must not inherit the master key
      └─ exec claude …
             └─ secrets live here, until the process exits
Claude Code Codex Grok 1Password · Bitwarden · pass bash · sudo

What you get

  • One vault token on disk instead of a fleet of .env files
  • Central rotation - change the vault, every future launch picks it up
  • Diffable manifests: which agent can reach what
  • Nothing secret on the command line (ps stays clean)
  • A demo that prints the real environment, not a success banner

Honest limits

  • Not “zero secrets on disk” - one service-account token remains
  • The agent can read its own environment (and so can anything as that user)
  • Manifests are blast-radius control, not containment - the agent can still open the token file
  • Root on the host can still read everything

Publishing forced five bug fixes (here-strings spilling to /tmp, the vault token riding along, missing environment scrub, exported bash functions, broken per-path sudoers). Full walkthrough: One Vault, Three Agents.

After install

Prefer not to pipe to bash? Download install.sh, read it, then bash install.sh. Pin with VAULTED_AGENT_VERSION=v0.1.3. Pass installer flags after bash -s -- (for example --user agent or --no-va to skip the short alias).

One credential stays on disk (1Password example; other backends in the README). Put the service-account token in op.env (mode 0640, readable by the service account), then activate a harness from the examples the installer left:

Configure token 
# write into op.env (0640 root:service-account), path printed by install.sh
printf 'OP_SERVICE_ACCOUNT_TOKEN=ops_...\n' | sudo tee op.env >/dev/null
sudo chmod 0640 op.env

# copy a harness example into place (drop the .example suffix)
sudo cp harnesses.d/claude.conf.example harnesses.d/claude.conf
